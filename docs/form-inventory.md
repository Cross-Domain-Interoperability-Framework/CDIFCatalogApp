# Form inventory: CoreDiscovery with stock renderers

First pass, 17 November 2026. This is step 2 of the prototype plan in [design.md](design.md).

**What was done.** The `CoreDiscovery` form was rendered with JSON Forms 3.8.0 and its stock Material
renderers, using the form files pinned in [`web/public/forms/PINNED.md`](../web/public/forms/PINNED.md).
Each of the five tabs was opened, and one empty entry was added to each repeating section.

**What this is not.** Nobody typed a real record into it, and no scientist has seen it. It finds
problems that are visible on an empty form. It says nothing yet about how the form feels in use.

## Summary

The form loads without console errors and all five tabs render. Simple fields (name, description,
dates, version, language, publisher, licence name and URL, place name) are usable as they are.

Three groups of problems need work before a test with scientists:

1. **A blank record already fails the form's own check in ways the author cannot fix** (section A).
2. **Either-or fields show unlabeled choices** (section B).
3. **Field labels and help text speak in schema terms** (section C).

## A. Problems the author cannot fix

The form reports 6 problems on a blank record. Four of them have no field on any tab.

| Problem reported | Why the author cannot fix it | Proposed handling |
|---|---|---|
| Record has no `@id` | No field in the layout sets it | Server assigns it on first save |
| Catalog record entry has no `@id` | No field in the layout sets it | Server assigns it |
| Catalog record entry has no `schema:about` | No field in the layout sets it | Server sets it to the record's `@id` |
| Catalog record `schema:additionalType` "must be string" | `defaults.json` supplies `{"@id": "dcat:CatalogRecord"}` but the generated form schema says the items are strings. The two files disagree. | Fix upstream in metadataBuildingBlocks; hide the field |
| Landing page URL is required | Reported against the whole record; the field does show "is a required property" | Keep, but see the note below |
| "must match then schema" | The same landing-page rule, reported a second time | Suppress the duplicate |

**Note on the landing page rule.** The form schema says: if `schema:distribution` is present, then
`schema:url` is required. `defaults.json` starts every record with `schema:distribution: []`, so the
rule fires on a blank record. Whether an empty distribution list should trigger it needs checking
against the source building block.

**Empty required fields are not flagged.** Name, identifier and date modified are marked required
but start as empty strings, and an empty string satisfies "required". A record with a blank title
passes the form. The server check has to catch this.

**The conformance declaration is not on the form** (`dcterms:conformsTo` appears nowhere in the
layout), which is as planned: the server stamps it.

## B. Either-or fields

The form schema has 45 either-or choices (`anyOf`). The stock renderer shows each as a row of tabs
labeled from the schema, and where the schema has no title the label is generated.

| Where | What the author sees | Proposed handling |
|---|---|---|
| Grants → Funding Agency | Two tabs labeled "ANYOF-0" and "OBJECT REFERENCE" | Organisation picker (ROR) |
| Keywords | A single blank text box, no label; the choice between plain text and a vocabulary term is not offered | Plain text for the prototype; vocabulary picker later |
| Same As | A single blank text box, no label | Label it "Other identifier" |
| Temporal Coverage | An empty row with no visible input | Start and end date fields |
| Resource Type, Additional Types | A one-column table with an unlabeled cell | Hide Resource Type (fixed value); dropdown for Additional Types |

Not yet examined: the choices inside Generated By, Derived From, Related Links, Measurement
Technique and Quality Measurements. They were not opened in this pass.

## C. Labels and help text

| Where | What the author sees | Proposed handling |
|---|---|---|
| Distributions | 20-odd fields with generated labels: "Schema Content Url", "Spdx Algorithm", "Dcterms Conforms To", "Schema Potential Action" | Hand-written layout for a distribution: URL, format, size; the rest behind "More" |
| Keywords help | A paragraph about parsing variability and `schema:DefinedTerm` | Rewrite for authors, upstream |
| Related Links help | Repository history ("Defined by schemaorgProperties/linkRole since 2026-09-23…") | Rewrite, upstream |
| Publishing Principles help | "FDOF digitalObjectMutability, RDA digitalObjectPolicy…" | Rewrite, upstream |
| Resource Type help | "a schema.org Class that specifies the expected information content…" | Hide the field |
| Variables | A new entry starts with Description set to "missing" | Remove the default upstream |
| Metadata Record tab | A field labeled "Type" with no explanation | Hide; server sets it |

Help text comes from the schema descriptions, which were written for schema authors. Either the
descriptions get a second, author-facing wording upstream, or the layout file overrides them.

## D. What already works

- Authors and contributors render as a compact table row: type, name, ORCID or identifier,
  affiliation. A new author is created as a `schema:Person`.
- Authors are stored in order (`@list`), as the profile requires.
- Licence is two fields, name and URL.
- Spatial coverage is a place name and a single bounding-box text field (south west north east).
  Usable, though a map would be better.
- Dates use a date picker.

## E. Library warning

Adding an entry to any expandable list (authors, grants, distributions) logs a React warning in
the browser console: a button nested inside a button, from the stock JSON Forms expand panel. The
form still works. It is a defect in the library's own renderer with this React and Material
version, and goes away for any list given a custom control.

## Early-stop check

The plan says to stop at this step if the stock form is unusable in ways the planned custom
controls do not address. That is not the case:

- Section A is handled by the server and by hiding fields. No custom control needed.
- Section B is mostly what the planned person, organisation and identifier controls are for.
  Temporal coverage is one more small control that was not in the plan.
- Section C is layout and wording work, not controls. It is larger than the plan allowed for,
  mainly the distribution section.

## Dry run, 23 November 2026

Day 9 of the build plan: re-enter five existing example records and fix what breaks. The five
were the profile's own examples: `exampleCDIFDiscoveryMinimal`, `exampleCDIFDiscovery`,
`exampleCDIFDiscoveryComplete`, `exampleCdifCore` and `exampleCdifCoreComplete`.

**How it was done, and what that leaves unproven.** Not by a person's hands. The first record was
entered in a browser by automation, which could not type into the date field or reliably into a
list entry, so its date and variable names were set through the saving address; it was then
checked and submitted with the form's own buttons. All five were then run by a script that
reshapes each example into the form's document, keeps only what the form has a field for, drops
the type markers the form cannot hold, saves it as a draft and submits it. That proves the
records the form can produce are accepted. It does not prove a person can find and fill the
fields; that is what day 10 is for.

**Result: all five submit valid.** Two faults found by filling in the form on the deployed
prototype the same day were fixed first (spaces around a pasted address; type markers the form
cannot hold), and without the second of those the records with variables did not submit.

### What could not be entered

| What | Where it shows | What to do |
|---|---|---|
| A related link's name and address | The layout addresses them as `target`, where the schema's property is `schema:target`. A link's kind could be entered, not what it links to. | Corrected the same day in `web/src/corrections.js`, which lays the right address over the layout when the form loads. A defect in the layout file; item 7 below |
| A variable's concept, unit code, range and method | The variable has three fields: name, unit, description. The report then recommends a concept link the form has no field for. | Add the fields, or stop recommending what cannot be entered |
| A place given as a point or a shape | Only a name and a bounding box can be entered | In the plan as the map control, after the spike |
| A person's or organisation's contact details, description and further identifiers | The pickers hold name, identifier and affiliation | Acceptable for the spike |
| A funder's identifier; the source catalog's address | No field | Acceptable for the spike |
| An entry given only as a reference to something described elsewhere (a contributor in one example, a provider in two) | The form has no way to point at a description held elsewhere; a person would type the name | By design |

### What a person would trip on

Seen in the browser on the first record:

- **A download is still the stock rendering**: some twenty fields labelled "Schema Content Url",
  "Spdx Algorithm *" and the like (section C). It is the largest piece of jargon left in the form.
- **A new variable's description arrived filled with the word "missing"** (item 3 below, not yet
  corrected in the form files), and was saved and submitted as the description. Corrected the
  same day in `web/src/corrections.js`, which takes that default out when the form loads.
- **The form shows its own count of faults** as a red badge beside a list (5 beside three
  variables) while the server reports nothing to fix.
- **"Kind of resource" shows `schema:Dataset`** as its value.
- The landing page is marked "is a required property" on a blank form (section A).

## Found for metadataBuildingBlocks

These are defects or questions in the source of the form files, not in this application:
All five were filed there on 17 November 2026: [#106](https://github.com/Cross-Domain-Interoperability-Framework/metadataBuildingBlocks/issues/106), [#107](https://github.com/Cross-Domain-Interoperability-Framework/metadataBuildingBlocks/issues/107), [#108](https://github.com/Cross-Domain-Interoperability-Framework/metadataBuildingBlocks/issues/108), [#109](https://github.com/Cross-Domain-Interoperability-Framework/metadataBuildingBlocks/issues/109), [#110](https://github.com/Cross-Domain-Interoperability-Framework/metadataBuildingBlocks/issues/110), in the order below.

1. `defaults.json` and the generated `schema.json` disagree on the shape of the catalog record's
   `schema:additionalType` items (object with `@id` versus string).
2. The landing-page rule fires on an empty `schema:distribution` list.
3. A new variable entry defaults its description to "missing".
4. Three required catalog-record properties (`@id`, `schema:about`, and the record's own `@id`)
   have no field in the layout, so the form can never report zero problems.
5. Found when the validation endpoint was built (17 November 2026): the generated form schema
   holds `@type` on people, organisations and licences as a single string, where the profile
   schema requires a list. A record straight from the form therefore fails the profile schema at
   every such node. The server converts it on the way in; the form files should agree with the
   schema instead.
6. Found on 23 November 2026: where the profile holds `@type` as a list (a measured variable, an
   activity, a funding identifier, a checksum, a source catalog's identifier), the generated form
   schema gives it no default and the layout has no field for it, so the record fails with a
   fault the author cannot fix. The server adds the marker on the way in. Filed as
   [#113](https://github.com/Cross-Domain-Interoperability-Framework/metadataBuildingBlocks/issues/113).
7. Found in the dry run, 23 November 2026, and not yet filed: in `uischema.json` the two controls
   under a related link are scoped `#/properties/target/properties/schema:name` and
   `.../schema:url`. The schema's property is `schema:target`, so what a link points to cannot
   be entered.
